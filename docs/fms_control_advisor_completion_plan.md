## 2026-10-27 분석 방법 확정 — 후속 구현 계약

**상태:** c7e8c0e5 위에서 사건별 식별·불확실성·종료 계약의 로컬 구현과 표적 통합 검증을 완료했다. 수치 후보·시간 진단·전후 판정·웹·내보내기, 실제 원본 형식의 PID 공급·PC 비교 adapter·파일 전송 왕복을 확인했다. 최종 소스/보존 근거는 최신 인수인계와 `.analysis/identified-analysis/final-verification.json`을 따른다. 실제 Tailscale 전송·기기 설치·반복 운영과 차량 개선은 아직 검증하지 않았다. 이 계약은 과거 ±1단계 수동 비교를 후속 개발 방법으로 삼는 설명보다 우선한다. Astra High의 기존 분석과 후속 검토를 반영했다.

### 1. 프로그램과 AI의 역할

기존 Python 분석 CLI를 확장한다. 수치 모델 추정·후보 재생·불확실성 계산은 프로그램이 수행하고 Codex는 결과와 실패 원인을 해석한다. **로컬 LLM은 도입하지 않는다.** 필요한 것은 대량 언어 추론이 아니라 재현 가능한 수치 계산이다. 같은 입력·버전·실행 설정·seed를 결과에 결합한다.

`candidate_lateral.py`의 차량 모델 역산, `candidate_pid.py`의 1차 응답+지연 모델과 실제 PID 재생, 기존 fit/select/holdout, 입력 묶음·반환·CAS·소비 관측·비교·원복을 재사용한다. 별도 PC 수집기나 범용 차량 시뮬레이터를 만들지 않는다. 6개 목표·Ki=0·수동 CustomSR·Factor/마찰/기타 정책 고정을 유지하고 실제 consumer 값으로 확인한다. 수동/P 전환 전체 주행 분석과 성공적 적용 이후 범위도 유지한다.

### 2. 입력과 항목별 알고리즘

횡방향 목표 곡률→최종 출력→조향각→yaw, 종방향 목표 가속→최종 SCC 요청→실제 가속을 원본 시각으로 분리한다. 단계별 시간차는 응답 진단이며 인과관계나 설정 정답으로 단정하지 않는다. 필터·포화·개입·센서 시각 불확실성을 함께 기록한다. 도착 시각이나 UI 축약 600점으로 지연을 추정하지 않는다.

| 항목 | 계산과 허용 결론 | 보류 조건 |
|---|---|---|
| CustomSR | 준정상 좌우 회전의 보정 조향각·독립 yaw/속도·stiffness/roll·기존 차량 모델로 강건 회귀. 유효 조향비와 범위 추정 | 좌우/속도별 불일치, 영점 문제, stiffness와 분리 불가. 기계적 실측비라고 부르지 않음 |
| LateralTorqueKf | SR/Factor/마찰 고정, 실제 FF·출력과 기존 PID/응답 모델로 지속 오차·출력 크기 평가 | 마찰/포화와 분리 불가, 독립 구간에서 방향 불일치. Kf는 FF 마찰 성분에도 작용하므로 단순 오차 비례식 금지 |
| LateralTorqueKpV | Kf 고정, 실제 PID 재생으로 추종·회복·오버슈트·출력 변동 평가 | 보호 지표 악화, 합당한 모델 간 추천 반전, 관측 출력/속도 범위 밖 |
| SteerActuatorDelay | 출력→조향각→yaw 지연과 시정수를 구분해 시험 범위·근거 제공 | 관측 지연을 설정값으로 복사하거나 고정 목표 이동만으로 최적값을 주장해야 함 |
| LatSmoothSec | 평활 전후 목표·이전 출력·프레임별 평활값/action_t로 잡음 감소와 회복 지연 비교 | 중간 신호 없음, 다음 모델 입력 변화의 효과를 평가할 근거 없음 |
| LongActuatorDelay | 최종 SCC 요청·jerk/StopReq→aEgo 응답을 가속/감속·속도별 추정해 시험 근거 제공 | ECU 내부 처리/센서 필터와 분리 불가, 출력/측정 시각 불명 |

시간 3개는 모델의 action_t와 후속 입력을 바꾼다. 현재 고정 로그만으로 소프트웨어 최적값을 확정하지 않는다. 기존 설정 변화 자료 또는 계획된 A/B가 필요하면 `experiment_required`로 구분한다. 시험 방향조차 뒷받침할 근거가 없으면 진단/보류만 반환한다. 단순 ±1단계 버튼 연결을 분석 완료로 판정하지 않는다.

필요 신호의 실제 기록 여부를 먼저 확인한다. 빠진 평활 이전 목표·프레임별 평활값/action_t가 분석에 필수이면 기존 observer에 최소 필드만 추가한다. 다른 신호로 대체하고 실측값이라고 표시하지 않는다.

### 3. 모델 선정·독립 검증·수치 판정

1. 회전 진입→유지→회복, 가감속의 사건 단위로 학습/선택/최종 검증을 분리한다. 같은 사건과 인접 상관 구간을 서로 다른 분할에 넣지 않는다. 설정 epoch·좌우·속도 조건을 보존한다.
2. 기존 1차+지연 모델을 기본으로 폐루프 잡음 영향을 다루는 예측오차 추정·잔차 검사를 보강한다. 모델 구조/계수/불확실성은 학습 자료에서 동결한다. 2차 모델은 학습 내부 검증에서 필요한 경우만 검토한다. 높은 응답 적합률을 지연 계수의 정확성으로 해석하지 않는다.
3. 주 지표 하나와 보호 지표를 후보 선택 전에 고정한다. 적용 전후 시험의 주 지표는 목표 추종 RMSE(m/s²)이며, 횡방향은 독립 yaw×속도, 종방향은 aEgo를 사용한다. 물리 응답 지연은 별도 진단이다. 오버슈트·출력 급변·포화·개입 빈도를 함께 평가한다. 최소 유효 개선량과 허용 악화 폭은 학습용 기존값 반복 사건의 변동·측정 해상도로 항목별 단위에 맞게 정한다. 근거 없이 일률적인 개선율을 만들지 않는다. 메뉴 단계는 설정 양자화 조건이며 효과 크기의 증거가 아니다. 적용 전 첫 8개 사건으로 기준을 동결하고 적용 후 첫 8개 완결 사건 또는 900초에 종료한다. 조건이 맞는 8쌍이 부족하면 판정 불가이며, 뒤의 유리한 사건으로 대체하지 않는다.
4. 사건 단위 bootstrap의 명목 95% 구간을 사용한다. 이는 통계 규칙이며 차량 안전 보장이나 인과 증명이 아니다. 독립 사건이 부족하면 억지로 구간을 만들지 않는다. seed·반복 횟수·수렴 오차·최대 계산 예산은 시험 전에 실행 설정에 동결한다.
5. 선택 자료로 최대 2개 후보와 우선순위를 정한 뒤 최종 검증 자료를 한 번 평가한다. 개선량 하한이 사전 최소효과를 넘고 보호 지표가 허용 범위를 만족해야 남긴다. 검증 실패 뒤 같은 검증 자료로 후보/문턱을 다시 조정하지 않는다. 새 독립 자료가 없으면 보류한다.
6. 여러 합당한 모델이나 좌우/속도에서 방향이 뒤집히거나 효과가 불확실성보다 작으면 현재값 유지로 종료한다. 보고서는 현재값·후보·단위·근거 사건·추정 범위·예상 효과의 한계·보류 사유를 기계 판독 결과와 그래프로 함께 남긴다.

### 4. 구현과 시험의 완료 조건

- 순서: 신호/소비 경로 확인과 단계별 원인 진단 → SR, Kf, Kp 추정·검증 보강 → 시간 3개의 시험 선택·판정 연결. 종방향은 독립 분석하되 여러 설정을 동시에 적용하지 않는다.
- 현장 전: 알려진 정답을 가진 별도 생성 모델로 추정 오차, 잡음·필터·포화·개입·설정 혼재에서 올바른 보류, PID 계산 일치, 독립 자료 누출 방지를 시험한다. 추정기와 동일한 생성 모델만으로 성공을 주장하지 않는다.
- 기존 동결 로그: 결정성·사건 분리·수치 안정성·후보/보류·입출력 연결을 확인한다. 정답 없는 로그의 실행 성공을 튜닝 정확도 PASS로 부르지 않는다. 변경된 분석 경로만 표적 검증하며 변경 없는 웹·전송·CAS 전체시험을 반복하지 않는다.
- 현장: 한 값 적용→실제 소비 확인→사전 정의한 동등 조건 비교. 개입/회복 표본은 적합에서 제외하되 개입 빈도와 회복 문제는 별도 결과로 보존한다. 개입 때문에 기록 세션을 중단하지 않는다. 악화 시 원복한다.
- 한 기준 epoch에서 최대 2개 후보, 미리 정한 사건 수와 최대 관찰 시간 안에서 개선/악화/판정 불가로 종료한다. 유리한 결과가 나올 때까지 기간이나 후보를 늘리지 않는다. 필요할 때만 원복 A로 환경 변화를 확인한다. 추가 시험에는 새 가설·누락 신호·환경 차이의 구체적 근거가 필요하다.
- 구현 완료는 원인 진단→근거 있는 후보 또는 보류→재현 가능한 보고서가 프로그램으로 실행되고 위 시험을 통과한 상태다. 실제 원격 전송과 실차 효과는 별도 검증 결과로 남긴다. 현재는 이 후속 계약의 구현/시험 전이다.

방법의 제한은 [공식 시스템 식별 예제](https://www.mathworks.com/help/ident/ug/building-and-estimating-process-models-using-system-identification-toolbox.html)의 폐루프 사례처럼 높은 응답 적합률과 큰 지연 추정 불확실성이 공존할 수 있다는 근거를 따른다. MATLAB 설치/도입 결정은 아니다.

**2026-10-27 원격 실행 추가:** 기존 콤마 자체 기능을 유지하고 분석 위치 `device`/`remote_pc`를 분리했다. 원격에서는 기록·consumer·현재값 조건부 적용을 유지하며 후보 계산 자식과 콤마 자동 전후 비교 해석을 실행하지 않는다. Codex가 기존 인증된 원격 연결로 동결 입력을 가져와 같은 Python 계산기를 PC에서 실행하고, 검증된 결과만 반환한다. 별도 PC 앱·상주 수집기·새 서버는 없다. 원격 전후 판단은 Codex가 PC 자료로 수행하며 콤마 자동 비교 완료로 표시하지 않는다. 첫 원본 대기·단절·모드/기준 변경 시 원격 작업을 대기 또는 무효화하며 로컬 분석으로 자동 전환하지 않는다. 주행 중 변경 허용은 현재 소비값·유효 제어·신선도·CAS 보호를 제거하는 뜻이 아니다. 개입·회복 표본만 제외하고 기록 세션은 유지한다.

원격 경로의 PC 검증은 기존 원본 재사용→동결 전송→기존 분석기 실행→반환→기기측 완료 seal→동일 입력 직접 계산의 report/graph 일치, 원격 Popen0·재전송 멱등·기준/모드 변경 보류로 수행했다. 첫 원본 대기 후 새 checkpoint 재개, 실행 위치 미확정 시 로컬 비교 차단, 파일 변조·링크·겹침·복사 중 변경 거부와 기록 세션 유지도 표적 검사했다. 실제 Tailscale 전송·기기 설치·IPC/ECU·주행 효과/부하는 현장 검증이 남는다. 설치·원격 실행 순서는 [사용 안내](fms_control_advisor_install_test.md)를 따른다.

## 3. 실행 위치와 데이터

```text
콤마: 기존 원본 로그 + 경량 집계/후보 + 기존 WebCarrot 표시·수동 적용
   ↕ 필요한 수치·완료 로그만 전송
폰/파이: 원격 통신 중계
   ↕ 기존 비공개 원격 연결
PC: 자동 수집·그래프·문제 구간 추출 → 작업 중 Codex 검토
```

원격 연결은 개발·검증용이다. 폰·파이·PC가 꺼져도 콤마의 기본 수집·분석·조회는 독립적으로 동작해야 한다. Codex가 매 제어 주기를 판단하거나 원격 통신이 제어 루프의 필수 조건이 되지 않는다. 별도 대형 폰 앱은 만들지 않으며, 먼저 현재 RoamADB/네트워크와 기존 WebSocket을 재사용할 수 있는지 확인한다.

폰의 웹캐럿 접속과 PC의 ADB 접속만으로 콤마까지 자동 라우팅되지는 않는다. 첫 연결에서 파이의 인터넷과 콤마 접근이 동시에 되는 실제 경로를 확인한다. 직접 접근이 가능하면 그 경로를 사용하고, 필요할 때만 화면 조작 없는 작은 수치 중계 통로를 연결한다. 화면 잠금·탭 종료·재연결의 영향도 한 번의 연결 시험에서 함께 확인한다.

필수 데이터는 다음으로 한정해 시작하고 실제 문제를 구분하는 데 필요한 신호만 추가한다.

| 용도 | 데이터 |
|---|---|
| 종방향 | 속도, 목표/실제 가속도, 출력 명령, 앞차 거리·상대속도, 제어 활성·포화·정지 상태 |
| 횡방향 | 조향각·명령, 목표 횡가속도, 보정된 회전/자세 반응, 당시 차량 구성·조향비·지연·사용 제어 경로 |
| 분석 제외 | 핸들·가속·제동 개입, 개입 전후 회복, 신호 무효·누락, 다른 설정/모드 변경 |
| 적용 비교 | 설정 원시값, 요청/저장 시점, 소비 관측, 차량·부팅·소스 시각 식별 |

원격 경향 관측은 보통 10~20Hz 선별 수신으로 시작한다. 현재 전송 경로의 서비스별 상한은 약 2~60Hz이며 최신값을 추려 보내므로 원본 전체 수신으로 취급하지 않는다. 빠른 진동·정밀 지연은 원래 주기로 기록된 로그를 사용한다. `carOutput`과 실제 필요한 상태의 전송 누락은 확인 후 연결한다. 도착 시각으로 신호를 맞추지 않고 콤마의 원본 시각과 유효성을 사용한다.

## 4. 정확도와 항목별 추천 방법

‘정확도 90%’처럼 근거 없는 하나의 수치를 약속하지 않는다. **유효 자료에서 반복되는 문제를 구분하고, 다른 구간에서도 후보가 일관되며, 적용 뒤 실제 악화/개선을 확인할 수 있는 수준**을 목표로 한다. 차이가 노이즈와 구분되지 않으면 현재값 유지가 정상 결과다.

| 항목군 | 가볍게 완성할 방법 | 남아 있는 필수 작업 |
|---|---|---|
| 토크 Factor·현재 모드의 조향비 | 독립적인 센서 융합 반응으로 직접 보정. fit/검증 구간 분리 | 실제 yaw·보정·지연·차량 구성·사용 callback 연결. 기존 offset 가정 수정 |
| 마찰·종횡 지연·smoothing·경로 offset | 반복 패턴 진단 후 해당 저장값과 원인이 대응될 때 후보 생성 | 단순 잔차나 총지연을 물리 마찰/저장 지연의 정답으로 오인하지 않는 대응 검증 |
| 종횡 P/I/F | 실제 사용되는 gain과 제어 상태를 확인하고 근거 있는 작은 후보를 주행 전후 비교 | 포화·FF·학습·지연과의 혼동 구분, 항목별 계산/후보 생성 및 현재 경로 반영 확인 |
| 가속·차간·앞차 반응·정지 관련 정책 | 기존 FMS 식과 명시한 사용자 목표를 기준으로 후보·전후 차이 제시 | 필요한 동적 상태 수집과 원본 식 재현. 현재 차량 반응 자체를 원하는 정책의 정답으로 삼지 않음 |

| 모드·미사용 경로 | 현재 사용 상태와 영향 설명 | NNFF/수동 조향비 등의 모드를 자동 변경하지 않으며 실제 미사용 Kd 등은 비활성 사유 표시 |

주요 수치 항목 43개와 맥락 항목 4개는 계속 평가 목록에 둔다. 첫 버전이라는 이유로 세 항목만 허용하는 제한은 두지 않는다. 항목마다 **추천 가능 / 현재값 유지 / 자료 부족 / 이 차량에서 미사용 / 계산 연결 미구현**을 구분한다. 실제 활성 경로에서 필요한 계산 연결은 구현해야 하며, 상태 이름만 바꾸어 완료 처리하지 않는다.

과거 오토튜너의 증감량은 후보 생성의 참고값이다. 모든 값에 같은 수정률을 적용하지 않고 현재 단위·메뉴 스텝·사용 경로·실제 자료를 확인한다. 작은 변경도 개선을 보장하지 않는다. 적용은 한 번에 한 항목으로 비교하며, 사용자의 기존 수동 설정 변경도 이력과 비교 구간에 반영한다. 첫 주행이라는 이유로 일괄 금지하지 않는다.

| C. 수집·추천 간소화 구현 | 원격 수집과 필요한 누락 신호 연결, 기본 분석 설정, 항목별 경량 후보/유지 판단 완성. 기존 백업·writer·비교 재사용 | PC에서 진행하며 차량 방문 불필요 |

단계마다 새 허가를 반복 요청하지 않는다. 현재 로컬 수정과 계획 갱신, 완료 후 auto 브랜치 커밋·푸시는 승인됐다. 기존 WIP·안정 브랜치와 기기 실행 상태는 바꾸지 않는다. 기기 설치·설정 변경은 이번 게시 승인과 별도다. 실제 사용 증거를 얻기 위한 설치용 개발 버전과 실차 검증 완료를 구분한다.

A는 대략 수분 단위의 첫 판별을 목표로 하며 연결이 되는지 같은 검사를 장시간 반복하지 않는다. 실제 소요 시간은 통신 상태에 달려 있다. 주행 횟수나 시간을 미리 고정하지 않고, 각 추가 측정이 다음 결정을 바꾸는 경우에만 수행한다. 코덱스 대화 작업 중 수치 묶음과 문제 구간을 조회하며, 별도 자동 실행 없이 대화 종료 후에도 계속 검토한다고 약속하지 않는다.

## 6. 자원 목표와 CPU 결정

아래 수치는 **측정 전 초기 개발 목표**이며 실측 PASS나 기존 기능의 강제 차단값이 아니다. 기기 자료에 따라 예산을 확정하고 변경 이유를 남긴다.

| 항목 | 초기 목표와 판별 |
|---|---|
| 상시 계산 | 기존 로그 재사용·온라인 집계. 원격 수집과 심층 계산은 파이/PC로 분리 |
| 분석 CPU | 수집 포함 5분 평균으로 단일 CPU 한 개 기준 5% 이하를 목표. 전체 CPU 평균으로 축소 표시하지 않음 |
| 분석 메모리 | 추가 분석 프로세스 PSS 80MiB 이내를 초기 목표로 두고, 주행 시간에 따라 계속 증가하지 않는지 확인 |
| 주기 작업 | 가벼운 후보 평가 5초 이내/5분을 목표. 긴 압축 해제·solver 탐색은 PC 심층 분석으로 이동 |
| 주행 영향 | baseline 변동을 넘는 제어 지연·누락·새 thermal throttling 악화가 없는지 확인. 예산 초과 시 새 계산을 보류하고 기존 제어는 유지 |
| 저장·통신 | 기존 원본을 재사용하고 필요한 자료만 복사·전송. 무제한 저장·동일 세션 반복 해제·영상 상시 전송 금지. 기존 원본 자동 삭제 없음 |

실제 동작 중인 기기의 스레드 affinity와 `/proc/stat` 20초 측정을 확인해 **오토튜너 전용 작업자와 그 분석 자식은 CPU 0, SCHED_OTHER, nice 15**를 시작 배치로 선정했다. 상속된 niceness가 이미 15보다 크면 더 낮은 우선순위를 유지한다. 수집/웹 서버와 기존 planner/control/model의 배치는 바꾸지 않는다. nice 값이나 코어 적용 실패는 실제 실효값과 함께 표시하며 성공으로 보고하지 않는다. PC·합성 모드에서는 호스트 배치를 변경하지 않는다.

선정 근거: CPU 0은 평균 72.5%, 측정 최대 77.8%였고 CPU 2보다 여유가 있었다. CPU 1의 센서 실시간 스레드와 CPU 3의 CAN 실시간 스레드, CPU 4~7의 planner/card/control/model 전용 작업을 피한다. CPU 7이 낮게 보인다고 모델과 공유하지 않는다. 이 측정은 정차 상태의 실제 서비스 부하이며 주행 중 오토튜너 ON 성능 검증은 아니다. 설치 후 기능 OFF/ON의 추가 부하와 지연을 비교해 실행 예산을 확정한다. 코어 지정만으로 주행 영향이 없다고 판정하지 않는다.

‘5초 튜닝’이라는 발화는 사용자가 ‘오토튜닝’으로 정정했다. 추천 주기를 5초로 변경하지 않으며 기본 5분·선택 3분을 유지한다. PC는 원격 관측·2차 검토만 보조하고 기본 수집·분석·후보 평가는 콤마 자체에서 수행한다.

## 7. 브랜치 완료 조건

1. **로컬 독립 동작:** 폰·파이·PC 연결 없이 수집·경량 분석·현재 결과 확인이 되고, 연결 끊김이 제어 기능에 영향을 주지 않는다.
2. **실제 자료 연결:** 이 차량의 종·횡방향 로그로 개입·회복·설정 변경을 구분하며 목표/실제 지표와 유효 시간·누락을 표시한다. 미완성 계산기와 자료 부족을 구분한다.
3. **실제 추천·비교:** B에서 확정한 필수 활성 항목의 누락 구현을 끝내고, 충분한 근거가 있을 때 후보/유지를 자동 제시한다. 주요 항목 목록을 줄여 완료한 것으로 바꾸지 않는다. 보편적인 전 항목 자동 최적화는 목표에 포함하지 않는다.
4. **실제 적용·복구:** 충분한 근거가 확보된 항목에서 명시적 저장·소비 관측·전후 비교·원복을 실제 기기로 확인한다. 저장 성공을 개선 성공으로 표시하지 않는다. 검증된 추천이 없는 축은 그 사실을 남기며 양축 추천 검증 완료로 표시하지 않는다.
5. **경량성과 보존:** 확정한 기기 자원 예산을 지키고 기존 FMS가 보존된다. 기능 비활성·제거 후에도 원래 FMS와 보존 데이터가 유지되도록 변경 묶음과 제거 목록을 갱신한다.

코드·연결·실차 검증 상태를 각각 기록한다. 필수 코드가 남으면 ‘구현 미완료’, 주행 자료가 부족하면 ‘해당 조건 미검증’으로 남긴다. 모든 주요 항목의 처리 상태와 한계를 공개하되, 이번 범위의 필수 미구현을 상세 화면 뒤에 숨겨 브랜치 완성으로 처리하지 않는다.

## 8. 구현·검증 방식

기존 모듈과 검증 결과를 재사용하고, 측정이 필요성을 보여준 부분만 수정한다. 새 기능·상당한 연결 수정은 AGY 제안 → Sol 통합·표적 검증으로 진행한다. 원인 불명·반복 실패·중대한 설계 변경만 Astra에 재검토한다. 이번 방향 검토는 기존 Astra 작업자를 재사용해 읽기 전용으로 완료했으며 추가 모델 탐색·제품 시험은 실행하지 않았다.

매 항목마다 전체 시험·모델 리뷰·보존 재구성을 반복하지 않는다. 변경 지점과 영향 범위 시험을 묶고, 기기 연결 한 번에 시작·관측·종료·복구를 확인한다. 최종 소스가 동결된 시점에 필요한 회귀와 보존/제거 검증을 한 번 수행한다. 실제 측정 결과가 없는 수치나 ‘테스트 수 증가’를 정확도·완성의 근거로 삼지 않는다.
